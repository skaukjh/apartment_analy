### 같이 걸리는 문제 4가지

1. **일반 회원은 캐시가 아예 예열되지 않는다** — `api/cron/tick/route.ts:186` 의
   `if (!useEnvKey && !cfgKey?.trim()) continue;` 가 `saveDashboardCache`(191행)보다
   **앞에** 있다. 개인 OpenAI 키 없는 회원은 AI 요약뿐 아니라 대시보드 캐시까지 건너뛴다.
2. **`api/ai/outlook/route.ts:79`** 가 `buildDashboardCached` 가 아니라 `buildDashboard`
   를 불러, 페이지가 이미 만든 것과 같은 18~70초 작업을 한 번 더 한다.
3. **DB 조회가 전부 직렬** — `dashboard.ts:290`(loadRegionMonthly)과 `dashboard.ts:328`
   (loadTradeCache 지역별 루프)이 서로 독립인데 순차로 돈다. 사용자 지역이 6개라
   loadTradeCache 만 로컬 기준 6초대.
4. **`dashboard_snapshot` 에 JSONB 필터용 인덱스가 없다** — 인덱스는 `captured_at desc`
   뿐인데(`0001_init.sql:40`) 조회는 `payload->>kind`·`payload->>userId` 로 건다.
   0.5MB 페이로드 행이 섞여 있어 행마다 JSONB 를 푼다.

### 적용한 수정 (2026-08-30)

**A. 만료 캐시를 먼저 보여주고 뒤에서 갱신 (stale-while-revalidate)**
요금제 판단이 필요한 Vercel Cron 이전 대신, **어느 요금제에서도 통하는 쪽**을 택했다.
`dashboard-cache.ts` 에 `DASHBOARD_CACHE_STALE_MS`(24시간)를 두고
`loadDashboardCacheEntry` 가 낡은 값도 `stale: true` 로 돌려준다.
`buildDashboardCached` 는 낡으면 **그 값을 그대로 응답하고 갱신은 `after()` 로 응답 뒤에**
돌린다. 같은 사용자의 중복 재조립은 `rebuilding` 맵으로 막는다.
캐시 정리 기준도 "3시간 지난 행"에서 "방금 넣은 것보다 오래된 행"으로 바꿨다 —
시간 기준으로 지우면 예열이 멈춘 동안 낡은 값을 보여줄 마지막 한 줄까지 사라진다.
곁들여 GitHub Actions cron 을 `0,30` → `7,37` 로 옮겼다 (정각은 무료 러너 큐가 가장 붐빈다).

**B. `saveDashboardCache` 를 AI 키 게이트 앞으로** — 개인 OpenAI 키 없는 회원도 이제 예열된다.

**C. AI 라우트가 대시보드를 다시 조립하지 않게** — `api/ai/outlook/route.ts` 와
`api/ai/evaluate/route.ts:73` 둘 다 `buildDashboardCached` 로. (evaluate 는 같은 파일
149행이 이미 캐시를 쓰고 있었는데 73행만 안 쓰고 있었다.)

**D. DB 조회 병렬화**

- `loadRegionMonthly`: 개수를 먼저 세어 페이지 수를 알아낸 뒤 전 페이지 동시 요청.
  정렬 키를 `(month, lawd_cd)` 로 못박아 페이지 경계에서 행이 겹치거나 빠지지 않게 했다.
  **실측 4.28초 → 2.23초, 행 10,192개와 순서 모두 순차 방식과 동일함을 확인.**
- `loadTradeCache`: 지역별 순차 루프 → `Promise.all`. 실패는 지역별로 따로 보고.
- 월 집계(1)와 원본 거래(3)를 동시에 띄우고 각자 필요한 자리에서 기다리게 바꿨다.

**E. 표현식 인덱스** — `supabase/migrations/0006_dashboard_snapshot_index.sql`.
**아직 실행 안 함** — Supabase SQL Editor 에 붙여넣어야 한다 (앱이 DDL 을 못 돌린다).

## 2026-08-30 — 송파한양1차 호가는 그 단지 값이 맞다 (삭제하지 않음)

의심의 근거였던 "2차한양 21.50억 우연의 일치"는 근거가 못 된다. 확인한 것:

- **`한양아파트` 64.26㎡ 자체 실거래**: 26-04-24 21.05억 · 26-05-09 20.70억 ·
  26-05-19 20.90억 · 26-06-27 20.60억 · **26-07-05 21.00억(직전)**.

즉 "그 단지 실거래와 맞지 않는다"는 전제 자체가 틀렸다 (직전 21.00억과 2.4% 차이).

KB시세를 사려 해도 그건 호가가 아니라 조사 시세라, "지금 이 매물 얼마"에는 상위평균가가
가장 가까운 대용치일 뿐이다. 목표가 7곳뿐인 지금 규모에 유료 API 를 붙일 이유는 약하다.

**그래서 택한 길 (②):** 호가를 자동으로 받아오려 하지 말고, **사람이 넣은 값의 나이를

## 2026-08-30 — 호가에 "본 날"을 함께 저장한다 (askingPriceAt)

### 무엇을 만들었나

- **`askingPriceAt`(YYYY-MM-DD)** 를 보유·목표 아파트 양쪽에 추가했다
  (`lib/types.ts`, `lib/store/config.ts` 의 zod, `PriceQuote` 까지 관통).
- **설정 화면에서 호가를 고치면 그날 날짜가 자동으로 함께 기록된다.** 값과 날짜를
  따로 두면 값만 고치고 날짜는 옛날 것이 남아 날짜가 거짓말을 하므로,
  `askingPricePatch()` 한 곳에 묶었다. 호가를 비우면 날짜도 지운다.
  평형 변경으로 호가가 실거래 중앙값으로 갱신되는 경로와 `autoFill` 경로도 같이 남긴다.
- **갭 카드 표시** (`components/dashboard/gap-section.tsx` 의 `AskingHint`):

  ```
  호가 19억 · 직전 실거래 대비 +1억5,000만 (+8.6%)
  호가 입력 2026-08-30 (오늘)
  ```

  30일(`ASKING_FRESHNESS_DAYS`)이 지나면 `⚠ 호가 입력 2026-07-01 (60일 전)` 로 바뀌고,
  날짜가 아예 없으면 `⚠ 호가 입력일 기록 없음` 이 뜬다.
  30일로 잡은 건 이 시장 호가가 한 달이면 눈에 띄게 움직이고, 더 짧게 끊으면
  매물 상황이 그대로인데도 경고가 상시로 켜져 있어서다.

- 설정 화면 "이전 내역" 요약에도 `호가 19억 (2026-08-30)` 처럼 날짜를 붙였다.

이게 애초에 "송파한양1차 21.5억 어디서 왔냐"를 되짚게 만든 문제의 답이다.

- **주의: 그 기간에 거래가 없던 평형은 어떤 방법으로도 안 나온다** (데이터가 없음)

### AI 요약 (오늘의 요약 /today)

- lib/ai/market-outlook.ts: 공식발표 10 + 기사 12 + 블로그 8 + 카페 8
- 검색어에 보유·목표 단지명 + 동 이름 포함
- **네이버 API 는 초당 제한(429)이 있어 반드시 순차 호출** (한꺼번에 던지면 전부 거부)
- 네이버 API 는 회원등급·조회수를 안 줌 → 광고 필터 + 구체성 점수로 대체
- 프롬프트에 근거 우선순위 명문화: 수치 > 공식발표 > 기사 > 개인의견
- 1시간 캐시 (lib/ai/outlook-cache.ts, dashboard_snapshot 재사용)
- 비용: 1회 약 6,700토큰 ≈ 5원. tick 이 시간당 1회 생성 → 하루 약 120원 상한

## 공유용 공개 앱 2개 (2026-08-26 신설)

원본 앱은 그대로 두고, 불특정 다수에게 링크로 뿌릴 앱 두 개를 갈라 만들었다.
**저장소 밖에 있다** — `skaukjh_project/public/` 아래 별도 폴더이고 아직 git 이 아니다.
Vercel CLI 로 직접 올렸으므로 로컬 폴더가 유일한 원본이다. (다음 할 일: git 저장소 만들기)

|           | 폴더                   | Vercel 프로젝트         | 화면                                     |
| --------- | ---------------------- | ----------------------- | ---------------------------------------- |
| 정책·시장 | `public/market-policy` | apartment-market-policy | 오늘의 요약 · 시장 동향 · 정책/뉴스      |
| 갈아타기  | `public/switch-plan`   | apartment-switch-plan   | 사용법 · 내 갈아타기 · 시뮬레이션 · 설정 |

### 구조상 알아둘 것

- **세 앱이 같은 Supabase 를 공유한다.** 실거래 캐시를 나누면 양쪽 다 반쪽이 된다.
- **계정이 없다.** 비밀번호 하나로 문만 열고(`APP_PASSWORD`, `lib/auth/gate.ts`),
  `lib/auth/server.ts` 가 원본과 같은 이름의 함수를 흉내 내 호출부를 안 고치고 계정 개념만 걷어냈다.
- **갈아타기 앱은 닉네임 + 개인 PIN 으로 설정 서랍을 가른다.** 설정 id 는 `pub:<닉네임>`.
  PIN 해시는 `dashboard_snapshot(kind='pub-pin')` 에 둔다 (마이그레이션 없이 쓰려고 기존 패턴을 따름).
  닉네임만으로 막으면 본인도 못 돌아온다 — 그래서 "중복 금지"가 아니라 "PIN 이 맞아야 열림"이다.
- **원본 앱의 크론은 `pub:` 사용자를 건너뛴다** (`listConfigUserIds`). 안 그러면 공개 사용자
  수만큼 브리핑을 보내려 하고 AI 를 돌린다.
- **AI 는 방문자가 부를 수 없다.** `resolveOpenAIKey()` 가 항상 거부하고, 캐시가 비어도
  생성하지 않고 `pending` 을 돌려준다. 원본 앱 크론이 만들어 둔 요약을 읽기만 한다.
- **실거래는 공개 앱이 수집하지 않는다** (`READ_ONLY_DATA`). 수집은 원본 앱 크론 몫.

### 비용의 병목은 Supabase 월 전송량(5GB)이다

용량(500MB 중 ~100MB)이 아니라 전송량이 먼저 찬다. 화면 한 번에 지역당 실거래 원본이
1MB 넘게 내려오기 때문이다. 두 겹으로 막았다.

- `lib/pipeline/my-dashboard-cache.ts` — 닉네임별 결과 캐시(Supabase, 3시간).
  3,161KB → 4.9KB, **99.8% 절감**. 설정 저장 시 `/api/config` 가 무효화한다.
  메모리 층은 일부러 두지 않았다 — 인스턴스마다 따로라 저장 후에도 낡은 화면이 남는다.
- `lib/store/market-data.ts` — 실거래 원본의 인스턴스별 메모리 캐시(30분, 8건).
  데이터가 덧붙기만 해서 메모리에 둬도 안전하다.

공개 앱의 공공API 키가 원본과 같다. 방문자가 "자동 계산"을 많이 누르면 원본 브리핑용
쿼터(일 1만)를 같이 먹는다 — 사람이 몰리면 공개 앱용 키를 따로 발급받아야 한다.

### 세금 계산에서 이번에 바로잡은 것

- **취득일은 잔금일**이다 (계약일 아님, 소득세법 시행령 제162조). 입력란 라벨에 명시.
- 요건 충족일을 `취득일 + n년` 으로 맞췄다 (예전에 +1일이 붙어 이틀 늦었다).
- **실거주는 개월 수가 아니라 `residenceSince`(거주 시작일)로 저장**한다.
  개월 수는 저장한 순간 멈춰서, 거주 2년을 채워 표1(6%)→표2(24%)로 뛰는 시점이 영영 안 온다.
  `residenceMonthsAt(holding, asOf)` 로 그 시점 기준으로 다시 센다 — 미래 가정도 함께 정확해졌다.
  취득 전 거주는 세지 않는다 (표2 의 거주기간은 "보유기간 중 거주한 기간").
